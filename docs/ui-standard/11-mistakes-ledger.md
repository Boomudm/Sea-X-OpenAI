# Mistakes ledger

This is a list of UI mistake classes that the user has caught and rejected, usually after the builder's own checks had passed. Each entry is one class of mistake, not one finding. The same class showed up on several screens or rounds, or the user caught it by hand.

How to use it:
- Read it before building a screen.
- Walk it again, entry by entry, before showing anything to the user.
- Every entry has a **Gate**. A gate is a check you can run in a browser or against the data, not a matter of opinion. Run it on the real rendered screen, in every theme and at every width you ship.

Conventions:
- "The user" is the person who approves the UI.
- A gate of "none yet" means a human has to check by eye until someone writes a check.
- Where a rule below contradicts an older habit, the user's rulings win. The rulings are summarised in the section that follows.

## User rulings that these entries apply

1. **Category colour, split by surface.**
   - Charts: categorical series get distinct hues, chosen by meaning for that chart. There is no fixed cap on how many. A long small tail may be folded into one grey "other" when that reads better.
   - Cards, lists and pills: colour means state only. Category is shown by icon or label, never by its own hue.
2. **Status colour as a chart series:** meaning wins. A series that means good, bad or in progress uses that status colour. Other series use non-status hues.
3. **State colours:**
   - Blue is actively running.
   - Grey is queued, scheduled, upcoming or ended.
   - Amber is waiting on the user's decision, and nothing else.
4. **Row click depends on table type.**
   - A table with a batch action: clicking the row body selects it, and the entity name link opens the detail.
   - Any other table: clicking the row opens the detail.
5. **Tap targets:** touch and mobile targets are at least 44 px. Dense desktop rows may be 40 px, with a 34 px header.
6. **Modal height by type:** a tabbed modal keeps one fixed height. A single-body detail modal hugs its content.
7. **Modal close:** backdrop click, the close button and Esc all go through one handler, and a dirty draft asks first.
8. **Grey in timelines:** an ended or exit segment may be grey, because grey is the ended state. "Data is never grey" applies to values, not states.
9. **Hover fade on chart marks** uses fill-opacity or stroke-opacity, never whole-element opacity.

## Honesty of text and numbers

| ID | Mistake (what the user saw) | Rule | Gate |
|---|---|---|---|
| UI-M-01 | A sentence not derived from data: a hard-coded explanation, tooltip or log line that is false for some state, such as a default branch claiming an action that never ran. | Every sentence or time about an entity comes from one function over one per-entity event history. Row, tooltip, modal, footer and log all call it. | Reconcile the sentence on every surface against the underlying history, including the default branch of every switch. |
| UI-M-02 | One quantity with several values: a "now" count with four different numbers on one page, with rates and attention counts differing per surface. | Define each number once (one function, one scope label). A scoped value names its scope, and an unlabelled value is the all-scope value. | List every surface that shows the number and check they match, or that each names a different scope. |
| UI-M-03 | State stale after an action. The modal header, chip, status line or log kept the old state. An inline switch changed the data and the toast said done, but the row, count and hero stayed old, so a second click sent the same value again. | After any action, the open modal and every row, count, hero and badge that reads the changed rows rebuild from the same state object before the toast. A toggle's next click is computed from the re-rendered state. Reopening shows only the new state. | Real-click each action type, then reopen the modal and diff row text before and after. Click a toggle twice and diff the row. |
| UI-M-04 | Another writer leaves the new surface stale: resolving an entity elsewhere left stale action cards, a re-check button, and a running check that wrote to the closed entity. | List every action that changes the entity a new surface shows. Each one must re-render the surface or exit it. | After each other writer fires, check the new surface for dead states. |
| UI-M-05 | The same entity offered different actions and words per surface. | One action set and one vocabulary per entity state, wherever it is opened. | Compare row actions against modal actions for each state. |
| UI-M-06 | Wrong or unshown arithmetic: releasing two items when only empty ones were removed, "12 - 19 - 0 = 0", profit ignoring a refund, an estimate off by one. | Derive from real counts, clamp visibly ("-7 to 0"), net out refunds, and print the same formula result in the dialog and the tooltip. | Check each formula against two fixtures, one of them an edge case. |
| UI-M-07 | Thin evidence shown with full confidence: a time-to-target from one sold unit, a 7-day median "explaining" two hours of slowness, a "little data" chip on the best seller. | Mark a low sample or a window mismatch in the cell, use its own word, and state the window on the estimate. | None yet; check each estimate's sample size and window by eye. |
| UI-M-08 | Ranking across units: sorting rates in different units looks authoritative and means nothing. | Sort only quantities in one unit. Normalise, or group by unit. | None yet. |
| UI-M-09 | The UI promises an effect it does not deliver: a confirm saying a rule can be cancelled when it cannot, a toast promising an audit row, a confirm that hides a side effect, a confirm with no numeric consequence. | Say what will happen, with numbers ("25 go back on sale, 6 keep running"), and build the promised effect or delete the sentence. | Read every confirm and toast, then verify the stated effect actually happened in the data. |
| UI-M-10 | A summary tile that drives no action, such as a success and failure count with no cause. | A summary tile names a cause the user can act on and clicks through to the rows behind it. A count with no drill-down and no decision is noise. | Whole-screen critique: for each tile ask what the user does next and whether it drills to rows. |
| UI-M-11 | A label that names something other than its value: a "last run" label showing a start time, or an end time beside a start-time tile. | Each label names exactly the quantity shown. Paired tiles use the same anchor (both start or both end). | Compare each label's value with the source table it claims to summarise. |
| UI-M-12 | A KPI period differs from its budget's period: a rolling 30-day figure compared with a monthly budget, and the remaining budget derived from the 30-day number. | A figure set against a budget uses the budget's own period, says the period in its label, and every place that shows the remainder reads one computed value. | Check "label period equals budget period", and grep that the remainder has one definition. |
| UI-M-13 | One fact with three totals: a headline, its legend and a table footer each summed a different set of rows (different window or filter). The same count also appeared in a tab badge, a filter chip and a footer. | A headline, its legend and its footer derive from the same rows. A different window is labelled on the figure. A count lives in the badge plus one in-view place (the one that also acts: filter or pager); footers carry sums only. | Sum the rows behind each figure and compare. Search the screen for each count shown twice. |
| UI-M-14 | Two related counts that a reader cannot reconcile (two overlapping populations, such as signed-up users versus purchasers), and two measures of one idea with one unlabelled bar and a bare percentage. | When populations overlap, show the bridge in figures derived in code from one snapshot, with the arithmetic in an info tooltip. Each measure gets its own label; a bar visualises one named measure against an explicit track. | Check that every pair of related counts adds up on screen. |
| UI-M-15 | A pager that counts the demo rows, not the population the chip states ("46" chip, "1-25 of 25" pager). | The pager counts the population that the chip or KPI states. If the data carries fewer rows, say so ("showing sample N of M"). | Compare each chip and KPI count with its pager total. |
| UI-M-16 | A wrong number waved off as preview data: a 0 / 0 headline excused as "just preview data" and shipped, caused by a real classification bug. | Every rendered number has an expected value from the data source beside it in the audit. A 0, empty or dash headline is a suspect, never an excuse. | A metric table in the audit: rendered value versus value computed from the data source. |
| UI-M-17 | Two readers of the same data disagree: one kept the last attribute per entity, another the first; an overview ignored a field the reference check read. | One shared helper per derived fact, plus a test that every reader returns the same answer. | A parity test against the reference reader. |
| UI-M-18 | A state that asks the user to decide, with no backend action that can leave it, so the badge can never clear. | Every state the UI asks the user to decide has a real action that exits it. Otherwise the copy says it is informational and the deferral is recorded. | List each decision state and name its exit writer. |
| UI-M-19 | Page chrome ignores the page state: error and empty states kept the status strip online, a live queue count and an enabled run button. | Status strip, tab badges and primary actions derive from the same state as the body. Error means unknown and disabled; empty means zero. | Force the error and empty states and read the chrome. |
| UI-M-20 | Data silently capped or fresh-looking when stale: only 40 of 164 lanes reachable, a source silent for three minutes drawn as live. | Every item is reachable (pager or "show more"), and stale or partial data shows a stale or partial state. | Count reachable items against total; age a data source and check the display. |
| UI-M-21 | An item missing from a queue that counts it: a decision shown in a row but absent from the blocker list, overview attention list and log. | One decision list feeds every queue, hero count and badge. | Search each decision id across every queue. |

## Colour and contrast

| ID | Mistake (what the user saw) | Rule | Gate |
|---|---|---|---|
| UI-M-22 | Amber used where no user decision exists: the system waiting on something, a source down, nothing to send, a customer reservation. | Amber only when the user must decide (ruling 3). System waiting is neutral or blue per the state rules. | Inventory every amber element and name the decision each one asks for. |
| UI-M-23 | Red for something that is not bad: a normal action button, a red hero on every sub-view, a global colour slab painting red where nothing is wrong. Good news shown in the error slot or error styling. | One red hero per incident, on the page that owns it. Elsewhere use a muted line with a link. Normal actions are neutral, and success or info outcomes use the success or info card. | Check each red element against a real failure. |
| UI-M-24 | One fact in two colours or two words: a reservation amber in one place and blue in another, broken red in one modal and grey in another. A waiting state grey in one bar and blue in another. | One fact, one colour, one wording, through one label and colour table (ruling 3 for state colours). | Compare chip colour and modal colour for the same state on every surface. |
| UI-M-25 | Extra hues beyond the product's palette used for category or status-like meaning (teal, violet, orange, pink), or a second red. | Colour encodes meaning. Cards, lists and pills use state colours only (ruling 1); categories take icon or label. In charts, distinct categories get distinct hues chosen by meaning for that chart. | Inventory distinct hues per surface and justify each by a meaning. |
| UI-M-26 | Data drawn grey, dim or inverted: grey split bars, the lowest-progress tile the brightest thing in dark mode, dim chart bars. | Data values take a saturated semantic colour. In dark mode the quietest value is the dimmest. Grey is for ended or queued states and a deliberate "other" fold, never for values (ruling 8). | Sample computed fill colours of every series in both themes. |
| UI-M-27 | Disabled controls unreadable: faded red danger buttons, then near-black text on grey at 1.2:1 in dark. Cards or notices that let background art show through, or text below 4.5:1. | Disabled means neutral and at least 4.5:1 text in both themes, using one token pair per theme with specificity so disabled always wins. Status cards are opaque in both themes. | Measure computed contrast on every state in both themes and assert the ratio. |
| UI-M-28 | Checked in one theme only: light reads brown not amber, "darker means faster" is false in dark, one bar was 72 px wide in light and full width in dark. | Every colour fix and every sentence about colour is verified in dark and light by computed value. A meter's width, computation and tone come from one class with no theme branch. | Review light and dark shots of the same state as a pair. |
| UI-M-29 | Categorical tones collide or drift: an outcome blue reused as a category blue, a category changing shade when the split changes, two "other" buckets in the same grey. | A category keeps its tone in every split. Category tones never reuse a status colour. Each "other" bucket has its own name and hatch. | Switch each split and compare tones; search for reused outcome colours. |
| UI-M-30 | Chart hue does not match the data's meaning: in/out drawn as four blues, per-item stacks as blue shades, channels, segments and funnel all as blue steps. | Series colours are distinct hues chosen by meaning (rulings 1 and 2), consistent across the series' list, legend and tooltip. | A stacked chart's series must be distinct hues or a single series. |
| UI-M-31 | An established identity colour forced into the category palette, such as tiers or categories that already have a production colour drawn as blue steps. | Established identity colours keep their production colours on every pill, bar and modal. Exempt only those, explicitly marked. | Compare identity elements with their production colours. |
| UI-M-32 | Finished progress drawn in an in-progress colour: 100% bars in blue. | State colour follows the outcome: done is green, in progress is blue. | Check bars at 0%, mid and 100%. |
| UI-M-33 | Opacity used to encode meaning: the current partial month drawn at half opacity (reads as disabled, then vanishes under hover fade), ended or paused rows dimmed whole. | A partial period keeps the normal series colour and says so in its axis label and tooltip. Only the status pill carries state; the row keeps normal ink. Hover fade uses fill-opacity (ruling 9). | Check that no opacity or row-level dim encodes meaning. Exception: a heatmap sequential scale may encode magnitude (08-charts.md). |
| UI-M-34 | CSS cascade surprise: a new global class collided with grid classes, a new rule lost to a more specific old one, a missing variant fell to neutral, a new box-shadow erased an existing ring, a hub-wide rule reshaped a view's control (a stepper boxed, a radio stretched, a select clipping a label). A short-viewport rule leaked into other pages importing the same stylesheet. | Scope new classes with a view prefix, never a bare shared class name. Verify the computed style on the state, not the source rule. When two rules set one property, compose them. A rule for one page goes under that page's root. A custom radio or checkbox pins its padding and size. | Read computed style on the state; check other importers of the stylesheet; diff marks before and after. |
| UI-M-35 | Chart hit areas painted black: a chart drawn without its wrapper class left hover rectangles at the default fill, so the plot sat on a black slab. | Every chart element carries the chart wrapper class that makes hit areas transparent. | Look for any solid slab behind bars. |

| UI-M-51 | A rail card squeezed to a title stub, because a tall sibling took the row. | The second card gets a minimum usable row height and the first tightens at short heights. | Check every rail at the shortest supported height. |
| UI-M-52 | The point of a form below the fold: a form's live preview sat at the bottom of the column and only 85 px showed. | A form's live preview is visible on open at the reference size. | UI-M-53 | The selection bar wraps: two selected rows grew the bar to 93 px and pushed the table down. | The selection bar replaces the toolbar at the same height. Overflow actions fold into an anchored overflow menu. | Compare bar height with toolbar height. |

## Menus, modals and flows

| ID | Mistake (what the user saw) | Rule | Gate |
|---|---|---|---|
| UI-M-54 | A menu not anchored to its button: menus inside modals or scrollers opened at screen centre or a corner. A centred modal used as a three-item action menu. | Pass the clicked button as the anchor everywhere, including inside modals and scrollers. An action list is an anchored menu, not a modal and not a drawer. | Click every menu trigger, inside modals and scrollers, and check the menu position. |
| UI-M-55 | Menu or modal stale after an action: the launching menu stayed open with the old actions, floating over other rows. | Every action closes its launching menu through one shared path. Reopening lists only the new state's actions. | After each action, assert no menu is open and that reopening matches the state. |
| UI-M-56 | Focus and keyboard failures: focus fell to the document body after Esc, a re-render, a confirm, a toggle or a batch apply. Arrow keys did nothing in a menu. A modal repainted by a one-second progress tick lost focus. | Store the opener and refocus it on close. A re-mount keeps the focused control. Menus rove with arrows, Home and End, and Esc returns to the trigger. Backdrop, close button and Esc share one handler and a dirty draft asks first (ruling 7). | Walk each flow by keyboard; after every action, the active element must not be the body. |
| UI-M-57 | A risky action badly placed or guarded: a red item mid-menu, autofocus on a destructive confirm, a batch publish with no confirm, no reason required for an irreversible action, a danger confirm that focused OK. | Risky items go last, after a separator, in red, and confirmed. Danger confirms focus Cancel. Irreversible actions need a reason. Batch actions confirm with a count. | Inspect menu order and the focused element of each confirm. |
| UI-M-58 | A control that does nothing: a toast stub, a dead-end list, a button opening a "0 items" dialog with Send enabled, a footer action that is a no-op in the current tab. | Every control works, or is disabled with a stated reason. An empty target refuses with its reason. | Real-click every control. |
| UI-M-59 | A silent disabled action, and an unchanged value shown as a change: a grey Save with no reason, "7% to 7%" rows. | A disabled action states why beside it, and the reason tracks typing. A before-and-after row shows only fields that changed. | Read each disabled control for an adjacent reason. |
| UI-M-60 | Misleading defaults and premature errors: a pause action defaulting to a source that is still recovering with zero items, a handoff defaulting to an entity with no source data, a red error under an untouched field. | No context means "all" or a forced choice. Default to an entity that has data. Validation shows after interaction or submit. | Open each form fresh and check defaults and error state. |
| UI-M-61 | Clicking a selectable row does not select it: only the tiny checkbox selected. Or the row-click rule was invented per table and differed across tables. | Follow the standard row-selection ergonomics in one shared table implementation (ruling 4): a batch-action table selects on a row-body click (Ctrl or Cmd toggles, Shift ranges, checkbox toggles), with the name link opening the detail. Other tables open the detail on a row click. In-row controls never select. Hover and pointer cursor on clickable rows. | Real-click a row body, then its switch (selection unchanged), in every table. |
| UI-M-62 | A live repaint resets the input under the cursor: polling re-rendered a search box and typed text came out reversed. A 30-second refresh swapped a timeline to Loading, unmounted the chart and closed the hover card. | Live updates patch rows, never a focused input; keep value and caret. A refresh of the same window keeps previous data on screen (stale-while-revalidate), read keys use a stable window and not "now", and hover state survives a same-data re-render. | Type during a live run; test that the view stays mounted across a refresh. |
| UI-M-63 | An icon name missing from the icon set: an unknown id rendered a blank gap inside buttons, or an invisible element pushed a button label off centre. | Every icon id resolves in the icon map, and an unknown id throws in the build. A centred button's label is centred; check for invisible content taking width. | Assert icon lookups; check label centring on every button. |

The "before" view is production byte for byte. Every backend state has a designed row. Never state a fact the backend cannot supply. | UI-M-78 | A real figure beside a contradicting untagged sample: a real "redemptions 0" next to sample sales with redemptions in the hundreds, and a footer calling a sample count real. | Every sample figure carries a sample tag in every place it renders, driven by a record flag and not set by hand per screen. Rows that feed two surfaces come from one row set. | Sweep every sample render for its tag. |
| UI-M-79 | An invented fact on a real person: sample dates, roles, tags, notes, histories and messages attached to real names, or the signed-in admin's name on an invented row. | A real name carries only snapshot facts. A missing field renders as a dash with a tip. Sample events use clearly fake people ("Sample customer A"). Real KPIs carry no sample tag. | Check every column and feed that shows a real row against the snapshot's keys. |
| UI-M-80 | A sample series that contradicts a real total beside it: signup, cumulative and histogram charts summed to numbers other than the real KPIs. | Anchor every sample series to the real totals it sits next to, then check each sum by eye. | Sum each chart against the adjacent KPI. |
| UI-M-81 | A sample person's facts from separate generators: a KPI said 20 orders, chips said 9 of 12 rows, a history entry dated differently from its order, every sample person's newest order had the same number. | One row list per person feeds the KPI, chips, status bar and every history or message widget. One reference-number sequence across people. | Reconcile each person's facts across every widget. |
| UI-M-82 | A real person's amount in a different, unlabelled metric than the list it echoes, and a bar scaled to its row maximum reading 100% for "30%". | A real figure uses the same metric and format as the list it echoes, and its column says which. A bar reads against an explicit track. A partial list ends with "N more not in the data". | Compare each echoed figure with its source list. |
| UI-M-83 | A not-yet-live policy presented as current: a new expiry rule shown as fact with sample "expired" rows while production never expired anything. | A new policy reads "New policy: ... (starts on ...)" everywhere it appears, from one helper. No sample event shows it as having happened. | Search the screen for the policy wording. |
| UI-M-84 | Sample data that looks real, or an action invalid for the state: a sample customer with a realistic email and long numeric ID, an already-expired item offering Close. | Sample contacts use reserved example domains and zero-padded IDs. A footer offers only actions valid for the record's state. An over-budget confirm states the overspend in red. | Inspect sample contacts; check footer actions per state. |
| UI-M-85 | Unsourced chrome: badge counts and a refresh countdown copied from a live shell into a static snapshot, a timer that never ran. | Badges and live timers render only when the demo has a source for them. A snapshot demo shows its snapshot time, and the refresh action says what it reloads. | For every number on screen, name its source. |

## Rejected anti-patterns

These patterns are rejected on sight, even when the rest of the screen is good. A hit means redesign first, not "approve with a note". Patterns that duplicate an entry above are folded into it (extra hues, low contrast, developer text, error styling for good news, hand-drawn bars, progress as text, same counts shown twice).

| ID | Mistake (what the user saw) | Rule | Gate |
|---|---|---|---|
| UI-M-86 | One tab with many segments and a long scroll: a switch card, a table, an attention list, ladders and history stacked, so finding one needed several screens of scrolling. A jump-to row or anchors only decorate it. | One view, one job. Split independent segments into sub-tabs, a segmented control or master-detail. The default view fits about one desktop viewport; long tables scroll inside their own container or paginate. | Count scroll heights of the default view of each tab. |
| UI-M-87 | A different look inside one product area: a tab using other cards, chips, tables, buttons or header sizes from its sibling tabs. | Match the area's existing standard components. | Compare the tab with its siblings component by component. |
| UI-M-88 | Mixing separate jobs because they share data: a demand queue, a timeline and legacy settings on one tab, instead of the approved sub-tab structure. | Each job gets its own view, as in the approved design. | Compare the tab structure with the approved design. |
| UI-M-89 | An expansion that repeats its row: cards in an opened row showing values already in the row's columns. | An expansion shows only what the row cannot: how a number was built, a chart, history. Keep its actions. Check each card for a value no column has before deleting it. | For each card in an expansion, find its value in the row. |
| UI-M-90 | Tall stat cells: a row of full-width KPI boxes, each a tall box with a small label above one number. | Use a compact KPI strip: one short row, with label and value close together. | Measure KPI cell height and width against a compact strip. |
| UI-M-91 | Filters on their own near-empty row: scope pickers alone on a row with nothing on the left, or a range on one row and scope pickers on the next. | Put the range, scope pickers, hint and "updated" time on one compact inline row. A long hint becomes an info tooltip. It wraps cleanly on narrow widths. | Look for toolbar rows with large empty areas. |
| UI-M-92 | A long full-width summary bar drawn as its own band. | Draw it compact, next to the table or chart it summarises, not as a full-width band. | Check each summary bar's width and placement. |
| UI-M-93 | A monochrome card grid: all black, white and grey, with nothing showing which card is live, done or ending. It reads as a wireframe. | Add colour by state, never by category (ruling 1): blue is in progress or taking part, green is goal reached, red is failed or blocked only, grey is upcoming or ended. Sold out is an expected state (grey). Time running out is shown as a bold countdown, not red. Each category keeps its own icon, not its own hue. Brand identity colours stay on their own mark. | Check that each card's state is visible at a glance. |
| UI-M-94 | An off-centre button label: a centred button whose label sits left or right of centre, caused by invisible content such as a missing icon rendering as empty. | Check the label is centred, and remove invisible content that takes width. | Compare label centre with button centre; search for empty icon or hidden-span output. |

## Process mistakes

| ID | Mistake (what the user saw) | Rule | Gate |
|---|---|---|---|
| UI-M-95 | The builder's self-QA counted as QA: a "600-state" check passed four rejected screens, and later a parity-only audit passed six defects it could not see. | An independent critic with its own screenshots and real clicks returns zero blockers and zero major findings before the user sees it. The critique covers the whole screen: duplicates, wasted height, related facts placed apart, reuse of components already approved in the demo, and interactions matching the layout (a split pane opens in the pane). Keep a measurement audit as a separate lens. | A critic round with its own screenshots and real clicks. |
| UI-M-96 | The builder showed screens without opening every shot: defects visible at a glance reached the user. | The builder opens and inspects every screenshot, in every theme and viewport, at full size. A peer's or judge's clean verdict does not replace this. Name the rejected patterns explicitly in every audit prompt, because an audit that does not name a pattern does not check it. | Checklist per shot; audit prompt lists the patterns. |
| UI-M-97 | A probe blind to the last bug: a check covered only hidden-overflow ancestors, a viewport-only sweep missed content below the fold, a state hook opened nothing so probes measured the wrong view. | A new probe must fail on the previous round's build before it counts as a gate. Sweeps scroll every inner scroller to its end. A hook that opens nothing is a failure. | Run the new probe against the previous build and confirm it fails. |
| UI-M-98 | A fix applied to one copy: a rule fixed in one of four places, a blocker wired into one list, a sibling tab keeping its own generator, a shared-table bug "fixed" in one table. | Search for every copy of the pattern and fix all of them in the same change. Fix shared code, not one table. A consistency probe reads every surface that tells the entity's story. | Search for every copy after the fix. |
| UI-M-99 | A readme claim never measured: "blue everywhere", "shell keeps its shape", "one formatter" while many lines kept the old form. | Any "everywhere", "always" or "never" claim is backed by probe output quoted in the report. | Quote the probe output for each such claim. |
| UI-M-100 | Hook-driven proof, not a real click: a demo hook opened a menu at a corner while the real click anchored fine, and the HTML looked right while the accessibility tree did not. | Prove interaction with real clicks, hover and keys. Read the accessibility tree, not the HTML. Run one browser per server, and re-run serially before calling a failure a defect. | Real-click plans for each flow. |
| UI-M-101 | A port drifts from the approved design: the real build was written from a summary of the demo, giving wrong bar colour and size, legend copy, chip tones, filter placement and state words. | A port starts from the demo's source and its screenshots per view, with shared label tables copied verbatim. | Side-by-side screenshot diff per view against the demo, plus a source audit before shipping. |
| UI-M-102 | A new tab that rebuilds a live tab: a new view duplicated eight of fourteen parts already in the existing view. | Before designing, list every live component of the area and classify each new part as duplicate, overlap or new. Extend the live view in place, keep its labels and columns, and mark only the new parts. A redesign lists what the old surface rendered and could do, and each item is kept, moved with a named home, or recorded as dropped. | A parity checklist from the live components, tick or cross per item. |
| UI-M-103 | Audit viewport taken from the device name: "a laptop" was audited at one size while the user's screenshot was a smaller size, where a grid span pushed a card to a third row. | Before a layout audit, measure the user's screenshot (image pixels divided by device pixel ratio, sidebar width, font scale). Audit at that viewport plus the breakpoint edges. | A viewport list that includes the measured size. |
| UI-M-104 | A critic calls inner scroll a cut: audits reported rows below a card's edge as "cut" when they scrolled inside the card behind an edge fade. | A layout defect is a card edge below the viewport, a cut figure, a cut chart, or a word broken mid-word. Rows past a card edge with a fade cue are inner scroll, which is by design. | Checks for missing cues, cut figures and broken headers. |
| UI-M-105 | Hash-only navigation reuses the page: a capture loop that changed only the URL fragment never reloaded, so every "state" shot showed the first view. | Each captured state loads a fresh page, or a cache-busting query. Assert the URL and view after load. | Screenshot a known-distinct state first. |
| UI-M-106 | Screenshot timing and redaction traps: a shot right after navigation was dim or blank (fade-in, first-compile), and a recompile re-rendered the page and wiped DOM redaction so real customer data reappeared. The theme did not switch because the app reads a cookie, not the OS setting. Polling pages never reached network idle. | Wait for a stable element, redact, screenshot immediately, then re-check the shot shows the placeholders. Never send a shot taken after a recompile without redoing redaction. Set the theme the way the app reads it. Use a load event plus a fixed wait on polling pages. | Inspect each saved shot for placeholders, theme and a fully loaded state. |

## Fixes that caused a new mistake

A fix that breaks something else is a mistake class too. Each row names the rule that would have prevented it.

| Fix | What it broke | Rule that would have prevented it |
|---|---|---|
| Disabled controls made neutral | Dark disabled danger buttons at 1.2:1 contrast (UI-M-27) | Measure a contrast fix in both themes by computed style and assert at least 4.5:1, not "not red". |
| Reason text rewritten for one branch | The default branch claimed an action that never ran (UI-M-01) | Re-run the consistency check over every branch, including the default. |
| Marker strip added for event pills | Two-line compact labels clipped (UI-M-65) and a tick with no legend key (UI-M-66) | A layout move re-runs the label, legend and overlap checks together. |
| New identity-palette classes | Coloured slabs through the layout grid (UI-M-23, UI-M-34) | New global class names are scoped or prefixed; check them for backgrounds. |
| An outline on a "no rate" tile | Erased the red "needs fix" ring on exactly the failing items (UI-M-34) | When a state adds a box-shadow, compose it with existing marks and diff marks before and after. |
| Read-only gating for phones | The whole list at 45% opacity and untappable (UI-M-42) | Gate writes, not reads. |
| A compact highlights row | A second boxed stat strip: twelve boxes before the timeline | Count competing emphases (at most three) after adding any strip. |
| A truncation rule for short viewports | Hid cost figures in a card head and squeezed a toolbar label (UI-M-48) | A truncation rule names its exact target, and a check asserts no figure is truncated. |
| Short-viewport rules under a shared root class | Leaked into other pages importing the same stylesheet (UI-M-34) | A rule for one page goes under that page's root class; read the stylesheet's other importers. |

## Append protocol

After every critic round, in the same commit cycle:

1. Add each new mistake class as the next `UI-M-nn` entry in its category. Deduplicate by class: one entry per class, never per finding. If the class exists, note the new round on the existing entry instead.
2. Give every new entry a gate. A gate must fail on the previous build before it counts. If no gate exists yet, write "none yet" and add one in that round or the next.
3. Apply each fix to every copy of the pattern, not only the one the critic pointed at (UI-M-98).
4. If a fix broke something else, add it to "Fixes that caused a new mistake" with the rule that would have prevented it.
5. Keep each entry to a few short lines. Move detail to that round's findings list (the list of findings written per critic round), not here.
6. Keep private data out of the ledger: no account names, credentials or customer data.
